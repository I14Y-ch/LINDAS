# i14y datasets to LINDAS

`dataset2lindas` is the incremental exporter for public i14y datasets. It publishes DCAT dataset metadata, distributions and optional SHACL structures to:

`https://lindas.admin.ch/fso/i14y`

It does not export `dcat:DataService` resources. When a distribution references a public i14y service, it may publish only the `dcat:accessService` link to that service IRI.

## Source inventory and incremental plan

The synchronizer scans every page of `GET /api/datasets` without filters. The source inventory retains only:

- the i14y dataset `id`;
- the first item in `identifiers` (the primary identifier);
- `system.modifiedAt`.

The primary identifier is the LINDAS dataset identity. Missing identifiers, ids, or duplicate primary identifiers stop the run rather than producing ambiguous RDF.

For `CLEAR_GRAPH=false`, the plan compares this inventory with existing `dcat:Dataset` resources in LINDAS:

| Situation                                       | Action                                   |
| ----------------------------------------------- | ---------------------------------------- |
| Dataset absent from LINDAS                      | Export it.                               |
| Dataset no longer present in i14y               | Delete it from LINDAS.                   |
| `system.modifiedAt` is inside the change window | Delete then re-export it.                |
| `system.modifiedAt` is missing or invalid       | Delete then re-export it conservatively. |
| Dataset is unchanged outside the window         | Do not create Turtle for it.             |

`I14Y_MODIFIED_LOOKBACK_HOURS` controls the window. Its default is 24 hours, extended to 96 hours on Monday to cover the weekend.

Before the workflow creates batches, it writes two artifacts:

- `dataset_sync_plan.json`: dataset ids to export and identifiers to delete;
- `dataset_source_manifest.json`: the frozen source inventory and the source count of datasets with a structure.

All batch jobs, optional catalogue generation and final metrics use the same manifest. A change in i14y during a workflow run cannot therefore change the source set halfway through publication.

## RDF model

The mapping follows the same mapping as DcatCatalog export on I14Y.

### Main resources

```text
Dataset:    https://register.ld.admin.ch/i14y/dataset/{primary-identifier}
Structure:  https://register.ld.admin.ch/i14y/dataset/{primary-identifier}/structure
Agent:      https://register.ld.admin.ch/i14y/agent/{publisher-identifier}
```

A dataset is emitted as `dcat:Dataset` with its DCAT, DCT, FOAF, vCard and SPDX metadata, including multilingual text, dates, distributions, contacts, periods, checksums, licences, formats, access URLs and download URLs.

Distributions and internal mapping resources are generated as deterministic skolem IRIs below the dataset URI. Publishers are shared IRIs, typed as `foaf:Agent`, `org:Organization` and `foaf:Organization`; concepts and datasets use the same agent URI. The agent is removed only after its last dataset or concept reference has disappeared.

Theme codes are linked to the versioned i14y concept vocabulary configured by:

```text
DATASET_THEME_CONCEPT_IDENTIFIER=DV_DCAT_DATASET_THEME
DATASET_THEME_CONCEPT_VERSION=1.1.0
```

The resulting IRI has the form:

```text
https://register.ld.admin.ch/i14y/concept/{theme-vocabulary}/{theme-code}/version/{theme-version}
```

### Data service links

For every distribution `accessServices` entry, the exporter calls `GET /api/dataservices/{id}`. It emits `dcat:accessService` only when the service has `publicationLevel: Public`.

No triples describing the DataService itself are generated. The endpoint is used solely to decide whether the link is allowed.

### Optional common catalogue

No `dcat:Catalog` and no `dcat:dataset` membership triples are generated by default.

`CREATE_DATASET_CATALOG=true` is an independent opt-in switch. It creates or completes:

```text
https://register.ld.admin.ch/i14y/catalog/datasets
```

and links the complete frozen source inventory with `dcat:dataset`. This switch is independent from `CLEAR_GRAPH`; setting it back to `false` does not delete an existing catalogue.

## Structures

For every exported dataset, the mapper requests:

```text
GET /api/datasets/{datasetId}/structures/exports/TTL
```

A `404` means that the dataset has no structure. Any other failure aborts the batch. The response body is decoded as UTF-8 before parsing, independently of an incorrect HTTP charset declaration.

For an available structure:

- the dataset is linked to `<dataset-uri>/structure` with `dct:conformsTo`;
- named `sh:NodeShape` resources and named external subjects are indexed from the structure using `dct:hasPart`;
- production shape IRIs under the dataset prefix are kept unchanged;
- RDF blank nodes are skolemized below `<dataset-uri>/structure/.well-known/genid/`.

The `dct:hasPart` index makes external subjects explicit owners of a structure. It permits safe cleanup when the last structure referencing such a subject is deleted.

## Turtle generation and deletion

Turtle is written incrementally through `DatasetStreamingTurtleWriter`. A temporary rdflib graph exists for one dataset or one structure only; the complete batch graph is never retained in memory. The resulting Turtle is UTF-8 and uses full IRIs.

During a replacement or deletion, the exporter:

1. removes external mapping `rdf:type` triples only when the resource has no other dataset or structure owner;
2. removes external structure parts only when no other structure has them in `dct:hasPart`;
3. deletes the local dataset subgraph by its dataset URI prefix, including distributions and skolemized nodes;
4. removes the optional catalogue membership for that dataset;
5. removes publisher agents that have no remaining concept or dataset publisher reference.

Links to external concepts, standards, themes, public access services and URLs are leaves. The dataset-side reference is deleted, but the external resource itself is not traversed as part of the dataset subgraph.

## Configuration

| Variable                                                                             | Default / purpose                                                           |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| `I14Y_DATASETS_API_URL`                                                              | `https://api.i14y.admin.ch/api/datasets`                                    |
| `I14Y_DATASERVICES_API_URL`                                                          | Public service endpoint used only to check `dcat:accessService` visibility. |
| `LINDAS_QUERY_URL`                                                                   | Query endpoint; defaults to `https://lindas.admin.ch/query`.                |
| `LINDAS_UPDATE_URL`                                                                  | Required for graph updates and Turtle uploads.                              |
| `TARGET_GRAPH`                                                                       | `https://lindas.admin.ch/fso/i14y`                                          |
| `DATASET_URI_BASE`                                                                   | `https://register.ld.admin.ch/i14y/dataset/`                                |
| `DATASERVICE_URI_BASE`                                                               | IRI base used only as the object of approved `dcat:accessService` links.    |
| `STARDOG_USER` / `STARDOG_PASSWORD`                                                  | Credentials for protected update endpoints.                                 |
| `I14Y_DATASET_PAGE_SIZE`                                                             | Source page size; defaults to `100`.                                        |
| `I14Y_API_RETRIES`                                                                   | Retry count for i14y calls; defaults to `10`.                               |
| `I14Y_MODIFIED_LOOKBACK_HOURS`                                                       | Incremental change window.                                                  |
| `DATASET_OUTPUT_FILE_NAME`                                                           | Base Turtle filename; defaults to `datasets.ttl`.                           |
| `CREATE_DATASET_CATALOG`                                                             | Enables the optional catalogue; defaults to `false`.                        |
| `DATASET_CATALOG_URI`                                                                | Optional catalogue IRI.                                                     |
| `DATASET_THEME_CONCEPT_IDENTIFIER` / `DATASET_THEME_CONCEPT_VERSION`                 | Theme vocabulary and version.                                               |
| `AGENT_URI_BASE`                                                                     | Shared publisher-agent URI base.                                            |
| `GRAPHDB_UPDATE_RETRIES`, `GRAPHDB_UPDATE_BACKOFF_MIN`, `GRAPHDB_UPDATE_BACKOFF_MAX` | Retry policy for replay-safe SPARQL updates.                                |
| `DEBUG_LOCAL_TEST`                                                                   | Enables the local TLS behavior used in restricted development environments. |

## Local usage

Install dependencies:

```bash
python -m pip install -r requirements.txt
```

Generate Turtle for one or more i14y dataset ids. This command does not upload anything:

```bash
python -m dataset2lindas.src.main \
  --dataset-ids <i14y-dataset-uuid>,<i14y-dataset-uuid> \
  --batch-index 0
```

The default output is `batch_0_datasets.ttl`. The same ids can be supplied through `BATCH_DATASET_IDS`.

To build the optional common catalogue from a frozen manifest:

```bash
$env:CREATE_DATASET_CATALOG = "true"
$env:I14Y_DATASET_MANIFEST_PATH = "reconciliation/dataset_source_manifest.json"
python -m dataset2lindas.src.main --catalog-only --output dataset_catalog.ttl
```

`--catalog-only` requires `CREATE_DATASET_CATALOG=true`. Without `I14Y_DATASET_MANIFEST_PATH`, it scans i14y again and should therefore not be used as a replacement for the workflow publication step.

## GitHub Actions

`.github/workflows/dataset_reusable_workflow.yml` is called by TEST, INT and PROD dataset workflows.

1. `get-datasets` scans i14y, obtains the source structure count, creates the plan and freezes the source manifest.
2. `process-batches` creates Turtle batches with up to five parallel i14y workers. Every batch is validated with `rapper`.
3. `reconcile-and-upload` clears the graph when requested, otherwise applies deletions, optionally generates the common catalogue, then uploads the validated Turtle files sequentially.
4. `verify-source-metrics` compares the frozen i14y dataset count and structure count with LINDAS. Any mismatch fails the workflow.

`dataset_graphdb_test_incremental_update.yml` runs on weekdays at 03:30 UTC. It uses the same concurrency group as `dataset_graphdb_test_full_lifecycle.yml`, so the destructive lifecycle test cannot overlap an incremental TEST update.

The full lifecycle workflow clears the TEST graph, imports all datasets, deletes them one by one using the production deletion method, removes orphaned publisher agents and requires the graph to contain zero triples. If it fails, it publishes the remaining graph as `remaining_graph.nt` for diagnosis.
